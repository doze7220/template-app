# COWORK_HANDOFF.md
## Cowork（設計AI／監査役）向け引き継ぎ資料（固定方針編）

---

### このファイルについて
* **目的**：Coworkの「OZ VectorEditor」プロジェクトのコンテキスト（Knowledge）としてアップロードする、**変化の少ない固定方針**をまとめたもの。
* **重要**：このファイルはアップロード時点のスナップショットであり、Coworkはこれをローカルファイルとしてライブ参照しない（毎回固定内容が読み込まれる）。そのため、**セッションごとに変わる現在の進捗・懸念事項はここには書かない**。
* **現在の状況を知りたい場合は、`D:\ozlab\ozvectoreditor\_doc\COWORK_STATUS.md` を直接読むこと。** このファイルはアップロードせず、ローカルに置いたまま毎セッション更新する運用にしている。
* このHANDOFF.md自体を修正した場合は、Coworkプロジェクトの「コンテキスト」欄への再アップロードをユーザーに依頼すること（Cowork側からは直接更新できない）。

---

### 0. この試験運用の位置づけ
本プロジェクトは、**NotebookLM（設計AI）＋ Google Antigravity（実装AI）→ Cowork（設計AI／監査役）＋ Claude Code（実装AI）** への移行を検証する試験運用を兼ねている。Coworkが設計AI役を実務レベルで代行できるかどうかを見ている。

さらに現在は、発注者側の「設計AI」を**リード設計AI**と**現場設計AI**の2役に分割して運用している（役割定義の正本は`PROJECT_AI_WORKFLOW.md`【登場人物（ロール）】節）。
*   **リード設計AI ＝ Gemini Notebook**: Phase規模（アーキテクチャに影響する文脈を持つ）の開発に着手する際、大局的な指針書「DIR」を発行する。
*   **現場設計AI ＝ Cowork（本セッション）**: リード設計AIが発行したDIR、または軽微な要件をもとに、REQ作成・RESの継続監査（チェック0/1/2）を行う。

※ この2役へのツール割り当ては本プロジェクト固有の運用メモであり、`PROJECT_AI_WORKFLOW.md`本体には特定ツール名を記載しない（同ファイル冒頭の記述方針を参照）。

### 1. Coworkの役割（＝現場設計AI）
* 仕様・設計のレビュー（Step 0の企画検討の相手）
* Claude Codeが作成するRESの継続的レビュー（監査）
* 進捗・計画のチェック
* **REQファイルの直接作成**：`_log/req/` へ、既存テンプレート（`_doc/TEMPLATE_REQ_*.md`）と命名規則に準拠して直接書き込む。チャットへの貼り付けは不要（ユーザーはVSCode/Antigravity側で確認する）。
* **RESファイルの直接読み込み・監査**：`_log/res/` を直接読む。
* **知識ベース参照**：`_log/req/`・`_log/res/`・`PROJECT_ARCHITECTURE.md` をgrep＋直接読み込みで都度参照する。NotebookLMのような手動登録は不要（ファイル保存＝即座に参照可能）。コーパスが将来大きくなった場合は、サブエージェントに横断調査を委任して要約のみ持ち帰る運用に切り替える。

### 1.5 常時参照すべき既存ドキュメント（全文はここに記載しない、パスのみ）
* **`_doc/PROJECT_AI_WORKFLOW.md`**：ワークフロー本体（旧v1/v2を統合済み、v2ファイルは廃止）。REQ/RESパターン（A〜G）の対応表・各テンプレートの使い分け・チェック0/1/2・Phaseクローズ手順など、運用ルールの正本はすべてこちらに一本化されている。新規REQのパターン判断時に参照する。固有名詞（AI製品名）は含まない普遍的な記述にしてある。
* **`PROJECT_CONSTITUTION.md`**：実装AI向けの絶対ルール（Vanilla JS縛り、状態と描画の分離、責務定義の義務等）。チェック1（ルール・責務違反監査）の判定基準として必須。
* **`PROJECT_ARCHITECTURE.md`**：フォルダ構造・モジュール責務マッピング。REQ作成時（対象ファイルの特定、既存責務との整合確認）と、RES監査時の両方で必須。
* **`_log/dir/`配下のDIRファイル**：Phase規模の開発に着手する際、リード設計AI（Gemini Notebook）が発行する大局的指針書。該当PhaseのREQ（`TEMPLATE_REQ_ImpretonPlanMake.md`）を作成する前に必ず読み込み、DIRの制約から逸脱していないかを確認する。

### 2. 採用しているワークフロー
* 旧v1をベースに、旧v2（受け入れ基準／検証証跡の必須化・REQ差し戻し権・監査深度の階層化・RES→REQ逆リンク・Phaseクローズ手順）から個別に取捨選択し、**`_doc/PROJECT_AI_WORKFLOW.md`へ統合済み**（v2ファイルは廃止）。現在の正式ルールは同ファイルを参照。ここには判断の理由（なぜ採用/不採用にしたか）のみ記録する：

| 項目                           | 判断               | 理由（要約）                                                                                                                                                         |
| ------------------------------ | ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 受け入れ基準／検証証跡の必須化 | **不採用**         | 意図とのズレは結局テストプレイでしか判定できない。スコープ逸脱はGit diffの方が確実に拾える。AIの自己申告テキストは信用度が低い上にトークンの無駄。                   |
| REQ差し戻し権                  | **不採用**         | パターンA（計画立案）は計画時の二重チェック（作成AI＋監査AI）で担保済み。パターンB/D（即時実行）もコミット前のRES監査＋revertの安全網で担保済み。                    |
| 監査深度の階層化（Lv1〜3）     | **形式上は不採用** | v2は「Lv判定は発注者が行う」前提だが、発注者（人間）側に技術的な判断力の限界がある。実質的な深度判断はCoworkが担う。人間向けの代替として「チェック0」を新設（3章）。 |
| RES→REQ逆リンク                | **採用**           | 低コスト（RES冒頭に1行）。実際にREQファイルの上書き事故を検知する手がかりとして機能することを実証済み（`COWORK_STATUS.md`のインシデント履歴参照）。                  |
| Phaseクローズ手順              | **採用（軽量版）** | 専用レポートファイルは作らず`COWORK_STATUS.md`に集約する。手順の詳細は`PROJECT_AI_WORKFLOW.md`3-5章を参照。                                                          |

* コンテキスト肥大化・トークン消費増大を避けるため、**Phase StepやInterrupt単位でチャットを区切る**。1つの区切りが終わったら新規チャットへ移行してよい（Coworkはファイルベースでコンテキストを再構築するため、記憶の連続性は失われない）。
* **雑談・アイデアの発散はclaude.ai側**で行う。
* **「仕様以前の実装機能の相談」（Step 0の企画検討）はCowork側**で行う。リポジトリの現状に根ざした議論が必要なため。
