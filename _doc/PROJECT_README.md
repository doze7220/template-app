# PROJECT_README.md
最初に読むもの。本プロジェクトの開発ワークフローに関わる文書群の見取り図と、発注者（人間）が実際に手を動かす手順をまとめる。

---

## 0. このドキュメントについて

本書は、AIにコーディングを行わせるための、**個人・少人数開発者向け**のワークフロー体系解説ドキュメントである。発注者（人間）自身がコードを直接検証できない前提のもとで、複数のAI（リード設計AI／現場設計AI／実装AI／監査）に役割を分担させ、DIR/REQ/RESという3種の文書を介して開発を進める。すべての役は Claude Code が、セッションとサブエージェントに分かれて担う。

**このワークフローの特徴**

* **事前の完璧な指示より、多段の監査で誤りを後から拾う**：REQへの抜粋転載やAIの自己申告は多少の漏れ・誤りを許容し、チェック0/1/2の監査、検証コマンド（ビルド・構文チェック等。定義されている場合）、Git diffレビュー、テストプレイといった後工程で拾う設計にしている。単一障害点を作らない。
* **合意形成のコストを最初から発生させない**：個人開発では意思決定権が発注者一人にあるため、複数人チームで必要になる説得・調整のプロセスを持たない。DIR/REQ/RESのすべてが、発注者の主観判断で完結する。
* **役割ごとにコンテキストを分ける**：方針策定（Phase親セッション）・実務設計（サブフェイズごとの子セッション）・実装（タスクごとのサブエージェント）・監査（新規コンテキストで起動する読み取り専用のサブエージェント）を分離し、各担い手が扱う情報量を必要な分だけに絞る。
* **絶対ルールと可変索引を分離する**：プロジェクト固有の絶対ルール（PROJECT_CONSTITUTION.md）と、実装が進むごとに変化する索引（PROJECT_ARCHITECTURE.md）を別文書にし、それぞれの陳腐化・混同を防ぐ。
* **実装AIのコンテキストを能動的に管理する**：実装AIはタスクごとに新規起動され、その都度記憶を失う。必要な責務情報だけを設計AIが選んでREQ/RESに載せることで、無関係な情報によるハルシネーションを防ぐ（詳細は`PROJECT_AI_WORKFLOW.md`の2-0節）。

### DIR / REQ / RESについて
本ワークフローの作業単位。詳細な運用ルールは`PROJECT_AI_WORKFLOW.md`を参照（ここでは概要のみ）。

* **DIR**：`Phase XX-00`（Phase親セッション）で発行する、Phase全体で1本の基礎設計方針。大ゴール・サブフェイズ分け・サブフェイズごとの実装要件を定め、「次に何をするか」を見失わないための地図として使う。途中変更は許容し、変更時は親セッションが直接書き換えて変更履歴を残す。保存先: `_log/dir/`
* **REQ**：現場設計AI（子セッション）が実装AIへ渡す作業指示書。DIRまたは軽微な要件をもとに作成する。保存先: `_log/req/`（タスク実行系など、チャットへ直接入力するREQは保存しない）
* **RES**：実装AIが作成する作業計画書・作業レポート。監査サブエージェントのチェック0/1/2の対象。保存先: `_log/res/`

### テンプレート一覧について
DIR/REQ/RESの各テンプレートは、作業ケースごとに使い分ける。**どのケースでどのテンプレートを使うかは`PROJECT_AI_WORKFLOW.md`の3-1節を正とする。** テンプレートは追加・改名される可能性があるため、本書には一覧を持たない（二重管理による齟齬を避けるため）。

REQテンプレートは`_doc/`、RESテンプレートは`_log/`に配置する（理由は2節を参照）。

```
│ └ agents/
│   ├ oz-implementer.md      実装AI

│ ├ PROJECT_AI_WORKFLOW.md
│ ├ PROJECT_README.md
│ ├ PROJECT_MILESTONE.md
│ ├ PROJECT_PHASE_TRANSITION_CLEANUP.md
│ ├ INITIAL_PROJECT_STARTUP.md
│ ├ TEMPLATE_DIR.md
│ ├ TEMPLATE_REQ*.md
│ ├ COWORK_HANDOFF.md
│ ├ COWORK_STATUS.md
│ └ COWORK_STATUS_CLOSED.md
└ _log/                      DIR/REQ/RESの実行ログ
  ├ dir/
  │ └ closed/                フェイズ大番号移行時にアーカイブ済みDIRを退避
  ├ req/
  │ └ closed/                フェイズ大番号移行時にアーカイブ済みREQを退避
  ├ res/
  │ └ closed/                フェイズ大番号移行時にアーカイブ済みRESを退避
  └ TEMPLATE_RES*.md
```

`closed/`への退避は`_doc/PROJECT_PHASE_TRANSITION_CLEANUP.md`が定める定型プロセスで、フェイズ大番号移行時にまとめて行う（詳細は同ファイル参照）。

`PROJECT_CONSTITUTION.md`・`PROJECT_ARCHITECTURE.md`のみルート直下に置く（実装AIがREQのヘッダーからパス参照するため）。それ以外の人間・設計AI向け資料は`_doc/`、実装AIとの日々のやり取り（DIR/REQ/RES）は`_log/`に集約する。

**REQテンプレートは`_doc/`、RESテンプレートは`_log/`に置く。** 実装AIは`_log/`を参照するため、実装AIが使わないREQテンプレート群が同じ場所にあると余計なコンテキストノイズになる。実装AIが実際に読み込むのはRESテンプレートのみである。

## 4. 反復サイクル（Phaseごと）

```
Phase親セッション（oz-dir-session）
  1. DIR作成
  ├─ 子セッション Phase XX-01（oz-req-session）
  │    2. REQ作成 → 3. RES作成 → 4. タスク単位コーディング（3〜4を繰り返す） → 5. RES終了
  ├─ 子セッション Phase XX-02 …（DIRが全て終わるまで2〜5を繰り返す）
  6. DIR終了（Phaseクローズ）
```

### DIR策定（`Phase XX-00`、Phase親セッション）
1. 新しいセッションで「`oz-dir-session` で Phase XX を始めて」と伝え、DIR（大ゴール・サブフェイズ分け・サブフェイズごとの実装要件）を相談して作らせる。**DIRを承認する。**

### サブフェイズ（`Phase XX-01`以降、親から起動される子セッション）
2. 親セッションに「次のサブフェイズを始めて」と伝えると、子セッションが起動する。子セッションを開き、詳細を詰めてREQを作らせる。**REQを承認する。**
3. 子セッションが実装AI（サブエージェント）にRES（計画書の原本）を作らせ、監査サブエージェントがチェック0/1/2を行う。合格すればそのままタスク実行へ進む（発注者の承認は不要。タスク数と概要の報告だけが届く）。
4. タスクごとに、実装AIが新規起動されて1タスクを実装し、検証コマンドが定義されていればその合否を確かめ、監査サブエージェントが差分を確認し、合格すればタスク単位でコミットする。発注者には1行の進捗報告が届く。「途中確認推奨」が付いたときだけ、任意で画面を見ればよい。
5. 全タスクが終わると、操作手順と期待結果の形でテストプレイの確認項目が届く。**テストプレイしてOKを出す。** 不具合があれば伝えると、子セッションが修正して再確認を依頼してくる。
6. OKを出すと、子セッションが `PROJECT_ARCHITECTURE.md`・`COWORK_STATUS.md` を更新して最終コミットし、完了報告を返す。親セッションに戻ると、親が確認してDIRの「サブフェイズ一覧」を完了にする。後続サブフェイズの見直しが必要ならDIRを書き換えて変更履歴に残す。次のサブフェイズへ（2に戻る）。

**途中で呼ばれるのは「停止条件」に当たったときだけ**（監査が発注者判断を求めた、修正を2回しても監査に通らない、REQの範囲外の変更が必要、AIが資料から答えられない質問、憲法・DIRとの食い違い）。呼ばれないあいだは順調に進んでいる。停止条件の正本は `.claude/skills/oz-req-session/SKILL.md`。

### Phase終了フェイズ
7. 親セッションでフェイズクローズ処理（`PROJECT_AI_WORKFLOW.md` 3-5節）を行い、`PROJECT_MILESTONE.md` を更新する。大番号が変わる場合は、次の親セッションの最初に `PROJECT_PHASE_TRANSITION_CLEANUP.md` の棚卸しを行う。

単発の Interrupt / Survey は、親を介さず新しいセッションで「`oz-req-session` で Interrupt（内容）を進めて」と伝えて行う。

## 5. ワークフロー経緯詳細（読まなくてよい）

以下は各設計判断の経緯メモ。ワークフローの運用そのものには不要な情報のため、読む必要はない。時系列順に並べている。

### なぜPROJECT_CONSTITUTION.md／PROJECT_ARCHITECTURE.mdを分離したか
2プロジェクト前（PHASE OUT: Cluster Stirring）では、絶対ルールと実装索引が1つのアーキテクチャ資料に同居し、しかも絶対ルールが文書内の複数箇所（0章・5章・6章・9章）に散在していた。加えて関数レベルの詳細索引（PROJECT_FUNCTION_INDEX.md）まで保持しており、コードの実態と資料の記述が度々乖離し、原因不明の不具合が多発した。次作（OZtone）でルールと索引を分離し、コードで分かることは資料に書かない方針にした。

### なぜDIRが生まれたか
当初（P1-1・P1-2）はNotebookLMがREQそのものを作成し、それをコピペしてAI-IDE側に渡していた。Claude Desktop導入によりCoworkが直接ファイルを読み書きできるようになったため、REQ作成をCoworkに直接担わせることを検討したが、NotebookLMでの壁打ち結果をREQレベルの技術的な情報として自分で直接プロンプトに書くのは不可能だと分かった。そこでNotebookLMにDIR（設計指針書）を作らせ、それをCoworkに読ませてREQを作らせる、という中間文書を挟む形にした。DIR導入はP1-3から。

### なぜCOWORK_HANDOFF.md／NOTEBOOK_HANDOFF.mdを分離したか
ワークフロー本体（`PROJECT_AI_WORKFLOW.md`）はツール名を含まない普遍的な役割構造として記述する方針のため、「現在どのツールがどの役を担っているか」というツール固有の運用情報は別ファイルに分離した。ツールを乗り換える際も、書き換えるのは運用メモ側だけで済む。※ `NOTEBOOK_HANDOFF.md`は2026-10のNotebookLM利用中止に伴い廃止した。

### なぜPROJECT_MILESTONE.mdを3種類に分けたか
* フェイズ分解（P1-1〜）：DIR発行のタイミングで印を付けて残す。DIRが正式な確定記録のため、記述が食い違えばDIR側を正とする。（2026-10以降、サブフェイズ分解はDIR側に一本化し、本ファイルにはPhase大番号のみを書く）
* 機能バックログ：完了項目は同期前に削除する。時間経過とともに実態と乖離していく性質のため。
* 将来構想（別プロダクト相当のもの）：粒度が異なるため物理的に別ファイルへ分離する。

### なぜ実装AIに開発資料を渡さないか
実装AIはタスクごとに新規チャットで起動し、その都度コンテキストを失う。この設計は「前タスクの文脈を持ち越さないことでスコープ外への波及を防ぐ」ためのものだが、その帰結として「作業に必要な情報はそのチャットで渡す文書にすべて含める」必要が生じる。ここで`PROJECT_ARCHITECTURE.md`を丸ごと渡すと、作業に無関係な責務情報がノイズとなりハルシネーションを誘発するため、必要な責務だけを設計AIが抜粋してREQ/RESに載せる方式を採った。REQの【関連する責務】節、計画書の『参照する責務』項目はこのために存在する。
※ 唯一の例外は計画立案系の工程である。「何が関係するかが未確定の状態から設計を起こす」工程では、事前に責務を絞ることが原理的にできないため。

### なぜ実装AIに開発資料を書き換えさせないか
Phase進行中に実装AIが`PROJECT_ARCHITECTURE.md`を書き換えると、同じ計画書を使う後続タスク（別チャット）の前提が、誰にも気づかれないまま変化する。実装AIは記憶を持たないため、自分が変更したことすら次のチャットでは知らない。そのため資料への影響は作業レポートに記録させるのみとし、反映は発注者側が行う。ただしPhase最終タスク（後続タスクが存在しない）のみ、実務コストとのバランスから例外としている。

### なぜInterruptとSurveyのテンプレートを分離したか
当初は1つのテンプレートで兼用し、調査（Survey）の際にREQ本文へ「コード修正の絶対禁止」を都度書き足す運用だった。しかしInterruptとSurveyは「コードを直せ」「コードに触るな」という正反対の中心命令を持つため、片方の許可がもう片方の絶対禁止になる。手順本文が「修正を実行すること」で固定されている状態で禁止だけを追記する運用は、いずれ書き漏れる。テンプレートを分離し、禁止をSurvey側の冒頭に内蔵した。

### なぜImmediately／unImmediatelyという命名をやめたか
初期は「即時実行か否か」でテンプレートを分けていたが、実際の分岐軸は「RESを新規作成するか、既存RESに追記するか」だった。名前と分岐軸が一致していないため選択時に毎回迷う状態が続いていた。追記型を`Additional`に統一し、`REQ名からRES名が導ける`という既存の命名規則（`ImpretonPlanMake`↔`ImpretonPlan`など）に揃えた。

### なぜNotebookLMをやめ、DIRを`Phase XX-00`に切り出したか
2026-10、運用コストの都合でNotebookLMの利用を中止し、リード設計AIの役もCoworkが担うことになった。方針を書いた本人がそのままREQまで書くと、自分の方針を自分で監査する形になる。そこでDIR策定を`Phase XX-00`という独立セッションに切り出し、各サブフェイズは別セッションでDIRを文書として読み直す運用にした。あわせてDIRの位置づけを、詳細仕様やアーキテクチャまで固める「北極星」から、「次に何をするか」「何が目的か」を見失わないための地図（大ゴール・サブフェイズ分け・実装要件）へ軽量化し、作業途中での変更を許容した。詳細仕様・アーキテクチャ設計は、実コードを見られる各サブフェイズのREQ作成時に詰める。

### なぜClaude Code単独運用にし、DIRセッションを親にしたか
2026-11、設計AI（Cowork）と実装AI（Claude Code）を別ツールで運用していた体制を、Claude Code単独に置き換えた。役ごとにコンテキストを分けるという従来の設計は、セッションとサブエージェントでそのまま再現できる。実装AIは「タスクごとに新規コンテキスト」のサブエージェントとし、指示は設計AIの要約ではなくREQ/RESのパスとテンプレート本文で渡す。監査も新規コンテキストのサブエージェントに分け、実装した側の思い込みを引き継がずに成果物と実差分だけで判定させる。あわせて、DIR策定セッションをPhaseの間ずっと生きる親とし、サブフェイズごとのREQセッションを子として起動する形にした。子は親の会話を持ち込まない新規コンテキストで起動してDIRを文書として読み直し、DIRの書き換えは親だけが行う（書き手の一本化）。
