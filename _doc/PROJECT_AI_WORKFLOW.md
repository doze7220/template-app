# OZFrameWorks AI駆動開発メソッド（発注者・設計AI専用マニュアル）

本ドキュメントは、人間（発注者）とリード設計AI／現場設計AIが、実装AIへ的確な作業指示（DIR/REQ）を出すための「発注ワークフロー」を定義したものである。

※ 実装AIのコンテキストノイズとなるため、**本ファイルは実装AIには参照させないこと**。実装AIが必要とする規範は、`PROJECT_CONSTITUTION.md` と各TEMPLATEファイル側で完結させる。
※ 本ドキュメントは特定のAI製品・ツール名を含まない、普遍的な運用ルールとして記述する。現時点でどのAI（ツール）が「リード設計AI」「現場設計AI」「実装AI」の各役を担っているかは、運用ツール側のメモ（例：`_doc/COWORK_HANDOFF.md`）を参照すること。

---

## 【登場人物（ロール）】

*   **発注者（頭脳）**: ユーザー（人間） ＋ 設計AI
    *   **リード設計AI**: フェイズ規模（アーキテクチャに影響する文脈を持つ）の開発に着手する際、`Phase XX-00`（DIR策定セッション）で、Phase全体の基礎設計方針「DIR」を発行する。
    *   **現場設計AI**: リード設計AIが発行したDIR、または軽微な要件をもとに、各サブフェイズ（`Phase XX-01`以降）で実装AIへのREQ作成・RES監査（チェック0/1/2）を担当する。
*   **作業者（手足）**: 実装AI

※ 発注者側の「設計AI」は、上記の通りリード／現場の2役に分かれる。同一AIが両役を兼ねてもよい。ただしその場合も、**DIR策定（`Phase XX-00`）と各サブフェイズのREQ作成は別セッションで行う**。DIR策定時の会話文脈を持ち込まず、DIRを文書として読み直すことで、DIRの不備や開発資料との食い違いに気づける立場を保つためである（規模の小さい開発ではDIR発行自体を省略し、現場設計AIがそのまま担当してよい）。

## 1. タスク規模の定義と用語

プロジェクトのタスクは、「文脈の連続性（タスク区分）」と「作業の複雑さ（アプローチ）」の2つの軸で柔軟に管理・運用される。

### 1-1. タスク区分（文脈の連続性）

*   **Phase（テーマ駆動型タスク）**
    *   **定義**: Phase全体で一つのテーマを持ち、アーキテクチャに影響を与えるような「連続した文脈」を必要とするタスク群（大規模リファクタリング、新機能群の追加、全体的なブラッシュアップなど）。
    *   **2つの型**:
        *   **ゴール型**: 達成目標を定めて開始するフェイズ（例：「キャンバスの拡縮・パン機能を入れる」）。実装を進める中でアイデアが膨らみ、細部フェイズが増えることもある。
        *   **気分型**: ゴールを定めずに開始するフェイズ（例：リファクタリング、UIブラッシュアップ）。
    *   **サブフェイズ分割**: Phaseはさらにサブフェイズごとに分解し、`Phase XX-ZZ`（Phase番号-サブフェイズ番号）といった表記で管理する。
        *   `Phase XX-00`: DIR策定セッション。Phase全体の大ゴール・サブフェイズ分け・サブフェイズごとの実装要件を定める（1-2節DIR参照）。
        *   `Phase XX-01`以降: 実装サブフェイズ。各サブフェイズは「明確な単一機能の作業」に相当し、1サブフェイズにつき設計AI側で1セッションを立て、REQ作成 → 計画書（RES）原本の作成 → タスク実行と監査までを行う。
    *   **終了条件**: Phaseの終了は常に「発注者（人間）の主観判断」による。ゴール型は「機能が使い物になった」と判断した時点、気分型は「現状で妥協できる」と判断した時点でクローズする。判定基準を事前に固定する必要はない（アジャイル的運用）。クローズ時の手順は3-5節を参照。

*   **Interrupt（単発・独立型タスク）**
    *   **定義**: 現在のPhaseのメインテーマとは直接関係しない、文脈の連続性を必要としない「単発で完結するタスク」の総称。
    *   不具合の修正（Bugfix）だけでなく、UIの微細な調整、既存機能の小拡張、パラメータのINI化などすべてを内包する。
    *   Interruptであっても、1回の作業で完結しない規模のものは存在する（例：Phase進行中に、実装文脈とは無関係なリファクタリングを先に行う必要が生じた場合、実装前に関連する不具合を潰す必要が生じた場合）。この場合は計画立案を伴うアプローチ（3-1節ケースA）を用いてよい。

### 1-2. DIR（設計指針書）/ REQ（作業指示）/ RES（作業レポート）

#### DIR（Directive）
* Phase（フェイズ規模・アーキテクチャに影響する文脈を持つ開発）に着手する際、`Phase XX-00`でリード設計AIが発行する、**Phase全体で1本の基礎設計方針**。
* 目的は、作業途中で「次に何をするか」「何のためにやっているか」を見失わないための地図を最初に立てることである。記載するのは「大ゴール（完了の目安を含む）」「やらないこと」「サブフェイズ一覧（進行状態つき）」「サブフェイズごとの実装要件」「変更履歴」に限る（`TEMPLATE_DIR.md`参照）。
* 実装要件は「完成したら何ができるか」をテストプレイで確認できる言葉で書く。詳細仕様・アーキテクチャ設計・対象ファイルの特定は、各サブフェイズのREQ作成時に現場設計AIが発注者と詰める。
* **作業途中での変更・方針転換は許容する。** 変更時はDIRファイルを直接書き換え、末尾の「変更履歴」に1行追記する（別版ファイルは作らない）。各サブフェイズのセッションは毎回DIRを読み直すため、実態との食い違いを放置しない。
* Phaseの進行状況（どのサブフェイズまで完了したか）の正本はDIRの「サブフェイズ一覧」とする。
* ファイル名: `YYMMDD_HHMM_DIR_PhaseXX-00_(Phase名).md`、保存先: `_log/dir/`。
* 規模の小さいPhaseや、Interrupt系のタスクではDIRを省略してよい（3-1節ケースA参照）。

すべての実装作業は「REQ → RES」の対で管理する。REQは「実装AIに対する正式な作業指示」、RESは「実装AIの作業結果を記録する正式な作業レポート」である。以後の修正・調査・リファクタリングは、このRESを起点として行う。

#### REQ（Request）
* 発注者が実装AIへ渡す作業指示書。作業目的、制約条件、対象ファイル、期待成果物を定義する。
* 実装AIはREQ以外の要求を推測せず、REQの範囲内でのみ作業を行う。
* REQには、**ファイルとして `_log/req/` に保存するもの**と、**チャットへ直接入力するもの**の2種がある（1-3節参照）。後者は、対象となる作業計画書（RES）がすでに正式な記録として存在する工程で用いるため、REQ自体をファイルとして残さない。

#### RES（Result Report）
* 実装AIが作業結果をまとめた作業レポート。実施内容、変更ファイル、作業方針、懸念事項、追加タスクなどを記録する。
* Phaseでは次工程の入力資料となる。

> 【運用上の注記】RESの完了報告（自己申告）は無条件には信用しない。実際の検証は、実装AIによる自己申告テキストではなく、**コミット前のGit diffレビュー**（REQで指定したファイル範囲と実差分の突合）と、**発注者自身によるテストプレイ**によって行う。この方針により、REQ/RESテンプレートに形式的な「受け入れ基準」「検証証跡」欄を必須項目として設けることはしない（トークンコストに見合わないため）。

### 1-3. ファイル名と相互リンク

*   **ファイルとして保存するREQ**: `YYMMDD_HHMM_(要件名).md`、保存先 `_log/req/`
    *   Phaseの計画立案は `PhaseXX-XX_作業概要`
    *   Interruptは `Interrupt_作業概要`、ただし特定Phaseステップに対して明確な場合は `Interrupt_PhaseXX-XX_作業概要`
    *   調査指示は `Survey_調査内容`
*   **チャットへ直接入力するREQ**: ファイル保存を行わない。該当するのは `TEMPLATE_REQ_TaskExecution_Lite.md` / `TEMPLATE_REQ_TaskExecution_Additional.md` / `TEMPLATE_REQ_TaskExecution_PlanningUpdate.md` / `TEMPLATE_REQ_Interrupt_Additional.md`。いずれも既存の作業計画書（RES）を対象とする指示であり、作業の記録は計画書側に残る。
*   **RESファイル名**: `YYMMDD_HHMM_RES_(REQ要件名).md`、保存先 `_log/res/`
    *   ファイル名定義はREQ内に含める。要件名部分は基本的にREQ要件名と同じとする。
*   **相互リンク**
    *   REQ → RES: REQ内に、出力すべきRESファイル名を明記する。
    *   RES → REQ: **RES冒頭に、参照元REQのファイル名を必ず記載させる。** タイムスタンプが異なるため、これがないと過去の追跡時に対応関係が壊れる（実際にREQファイルの上書き事故を検知する手がかりとなった実例あり）。
    *   チャット直接入力のREQには参照元ファイルが存在しないため、この相互リンクは適用されない。追跡は計画書（RES）側の記述で行う。

### 1-4. 作業規模とアプローチの選択（運用の柔軟性）

*   **大規模・複雑な作業（事前計画を伴うアプローチ）**: アーキテクチャの変更を伴う場合や、修正箇所が複数にまたがりハルシネーションのリスクがある場合は、必ず事前の計画立案を行わせ、タスクを分割してから順次実行させる。
*   **小規模・明確な作業（即時実行アプローチ）**: 修正箇所やロジックが明確であり、単一のタスクとして安全に完結できると判断した場合は、事前計画を立てず、単一の作業指示のみで即座に実行・解決させる。

## 2. 実装AIのコンテキスト設計とスコープ規範

### 2-0. コンテキストの原則

実装AIは、**計画立案・各実装タスクごとに新規チャットで起動し、その都度コンテキストを完全にリセットする**。これは以下を意図した設計である。

*   前タスクの文脈を持ち越さないことで、スコープ外への波及・「ついでの修正」を構造的に防ぐ。
*   作業に不要な責務情報を実装AIに与えない（無関係な情報はノイズとなり、ハルシネーションを誘発するため）。

この結果、実装AIは自身の過去の作業内容を一切記憶していない。**作業に必要な情報は、そのチャットで渡される文書（REQ、または計画書としてのRES）にすべて含まれていなければならない。** これが、REQの【関連する責務】節および計画書（RES）の『参照する責務』項目が必須である理由である。

同じ理由により、**実装AIには開発資料（`PROJECT_ARCHITECTURE.md`）を直接参照させない**（計画立案系の工程を除く）。責務情報の抽出・搬送は、以下の役割分担で行う。


| 経路                                      | 責務を抽出する者       | 搬送する文書                                                                                                                       |
| ----------------------------------------- | ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| 即時実行（Interrupt / Survey）            | 現場設計AI             | REQの【関連する責務】節                                                                                                            |
| 計画立案を伴う（Phase / 大規模Interrupt） | 実装AI（計画チャット） | 計画書（RES）の『参照する責務』項目                                                                                                |
| 計画書に対するタスク実行・追記            | 既存の計画書を継承     | 計画書（RES）の『参照する責務』項目。計画時に想定されていない責務が必要な場合のみ、REQに【関連する責務】節を設けて現場設計AIが補う |

計画立案系の工程（`ImpretonPlanMake` / `Survey_PlanMake` / `PlanningUpdate`）でのみ、実装AIは開発資料の全体を参照する。これは「何が関係するかが未確定の状態から設計を起こす／組み替える」工程であり、事前に責務を絞ることが原理的にできないためである。ただしその抜粋内容は、現場設計AIのチェック1（3-3節）で検証する。

**実装AIに開発資料（`PROJECT_ARCHITECTURE.md`）本体を書き換えさせてはならない。** 資料への影響は作業レポートに記述させるのみとし、実際の反映は発注者側（人間＋設計AI）が3-4節・3-5節の手順で行う。Phase進行中に資料が実装AIによって書き換わると、同じ計画書を使う後続タスク（別チャット）の前提が、誰にも気づかれないまま変化するためである。
ただし、Phase最終タスクにおける資料への反映のみ例外とする（`ImpretonPlanMake` の固定タスク。後続タスクが存在せず、前提が動く危険がないため）。

### 2-1. スコープ規範

*   REQに明記されていないファイルは、閲覧はしてよいが**変更してはならない**。
*   「ついでの整形」「不要に見えるコードの削除」「命名の改善」は、明示指示がない限り禁止。
*   **実装AIとの対話は最小限にとどめる**（禁止ではない）。仕様のすり合わせ・設計の妥当性検証は、可能な限り発注者側（人間＋リード設計AI／現場設計AI）で事前に完了させ、実装AIには可能な限り精緻なDIR/REQを渡す。これはトークン従量課金コストの節約が目的であり、壁打ちそのものを一切禁じるものではない。
*   ただし、実装AIが作業中に真に判断できない曖昧点に遭遇した場合は、**推測で進めず**、作業を中断して疑問点を簡潔に1つ報告した上で発注者の回答を待ってよい。

## 3. 作業ワークフロー

### 3-1. 【Step 0: 企画検討と要求定義（発注者のみ）】

発注者間（人間＋リード設計AI／現場設計AI）でアーキテクチャを議論し、作業規模に応じて以下から最適なDIR/REQ/RESの組み合わせを選択する。

| ケース                                                               | 発注（DIR/REQ）                                                                  | 応答（RES）                                         |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------- | --------------------------------------------------- |
| A. Phase規模の本格的な実装（アーキテクチャに影響する文脈を持つ開発） | `Phase XX-00`でDIRを発行 → サブフェイズごとに`TEMPLATE_REQ_ImpretonPlanMake.md`を作成 | `TEMPLATE_RES_ImpretonPlan.md`                      |
| B. 軽微な新規作業（単一タスク規模）                                  | `TEMPLATE_REQ_Interrupt.md`（計画なしで直接作業）                                | `TEMPLATE_RES_Interrupt.md`                         |
| C. 完了済み作業への追加要件・バグ修正                                | `TEMPLATE_REQ_Interrupt_Additional.md`                                           | `TEMPLATE_RES_Additional.md`（既存RESの末尾に追記） |
| D. 時系列が離れた過去のバグ修正                                      | `TEMPLATE_REQ_Interrupt.md`                                                      | `TEMPLATE_RES_Interrupt.md`（新規に単独レポート）   |
| E. 調査・コード監査（単一タスク規模）                                | `TEMPLATE_REQ_Survey_Interrupt.md`                                               | `TEMPLATE_RES_Survey.md`                            |
| F. 調査・コード監査（複数タスク規模）                                | `TEMPLATE_REQ_Survey_PlanMake.md`                                                | `TEMPLATE_RES_SurveyPlan.md`                        |
| G. 進行中計画の、未着手タスクへの軽微な要件追加                      | `TEMPLATE_REQ_TaskExecution_PlanningUpdate.md`                                   | 既存の計画書を直接更新（別ファイルは作らない）      |

補足：
*   **A**: まず`Phase XX-00`のセッションで、リード設計AIが発注者と相談してPhase全体の`DIR`を発行する（1-2節DIR定義参照）。以後、サブフェイズ（`Phase XX-01`以降）ごとに新しいセッションを立て、現場設計AIはDIRの該当サブフェイズ節を起点に発注者と詳細仕様を詰め、`TEMPLATE_REQ_ImpretonPlanMake.md`を作成し、実装AIに詳細計画（RES）を立案させる。規模の小さいPhaseではDIR工程を省略し、現場設計AIが直接`TEMPLATE_REQ_ImpretonPlanMake.md`から開始してよい。計画立案後は、`TEMPLATE_REQ_TaskExecution_Lite.md` か `TEMPLATE_REQ_TaskExecution_Additional.md` を用いて、実装AIに「1タスク＝1チャット」で段階的にタスクを実行させ、タスクごとに作業レポートへ追記させる（2-0節参照）。1回で完結しない規模のInterruptも、この経路を用いる。
*   **C**: 追記先は「既存RESの末尾」であり、Phase進行中の差し込み作業であれば作業計画書（`RES_ImpretonPlan`）の末尾、単発Interruptの事後修正であればその作業レポートの末尾となる。**対象がすでに完了した作業である**点で、G およびタスク実行系の追加指示とは区別する（下記「追加系3経路の使い分け」参照）。
*   **D**: 過去の文脈を引きずらせないため、意図的に新規の単独レポートを立てさせる。
*   **E / F**: 目的は「実装AIの勝手な推測やコード改変を防ぎ、現在のコードの事実のみを抽出させる」こと。コード修正の絶対禁止は、Survey系テンプレートの冒頭に内蔵されているため、REQ発行のたびに個別に厳命する必要はない。
*   **G**: 完了済みタスクの `[x]` ステータス・記述には一切触れず、未着手タスクの内容とアーキテクチャ設計のみを拡張する。前提が崩れるほどの大規模な計画破綻ではなく、あくまで軽微な要件追加を想定した経路。この経路ではソースコードを一切変更しない（計画書ファイルの書き換えのみ）。

#### 追加系3経路の使い分け

いずれも「既存の計画に対する追加」であるため混同しやすい。**対象タスクがどの時点にあるか**で選択する。

| テンプレート                                              | 対象タスクの状態                                     | コード修正 | 書き込み先                       |
| --------------------------------------------------------- | ---------------------------------------------------- | ---------- | -------------------------------- |
| `TEMPLATE_REQ_TaskExecution_PlanningUpdate.md`（ケースG） | **未着手**（まだ実行指示を出していない）             | 行わない   | 計画書の該当タスク定義を書き換え |
| `TEMPLATE_REQ_TaskExecution_Additional.md`                | **これから実行する**（実行指示と同時に仕様を上乗せ） | 行う       | 計画書の該当タスク欄             |
| `TEMPLATE_REQ_Interrupt_Additional.md`（ケースC）         | **完了済み**（事後の追加・修正）                     | 行う       | 既存RESの末尾（追記型RES断片）   |

### 3-2. 【Step 1: 計画立案（REQ → RES）】※計画立案を伴うREQのみ

発注者が実装AIへREQを投げ、実装AI自身に自分の理解度に基づいた細かなタスクリスト（RES）を構築させる。

### 3-3. 【Step 2: RES監査 → 作業実行（RES → Code）】

発注者（設計AI）は、上がってきた作業計画書（RES）に対し、必ず以下の**3つのチェックを観点ごとに独立して**行う（視点のぼやけや見落としを防ぐため、観点を混ぜて判定しない）。3観点を1回の監査でまとめて行ってもよいが、その場合も観点ごとに順に判定し、判定結果を観点ごとに分けて出す。

1.  **チェック0（方向性・意図整合性）**: RESの作業内容が、そもそもREQ・発注者の意図の方向性と合っているか。
2.  **チェック1（ルール・責務違反／アーキテクチャ監査）**: `PROJECT_CONSTITUTION.md` 3章の絶対禁止事項（責務分離の崩れ、特定モジュールの肥大化、描画層・UIへの状態混入など）に反し、アーキテクチャの根幹を崩す設計になっていないか。あわせて、RESの『参照する責務』が開発資料（`PROJECT_ARCHITECTURE.md`）の記述と一致しているか、および実コードの実態と矛盾していないかを確認する（この項目は実装AIが抽出したものであり、以後のタスク実行における唯一の責務情報源となるため）。
3.  **チェック2（スコープ・粒度）**: 変更単位が極力ファイル単位に分割され、実装AIがコンテキストを混同しない（安全なスコープに収まっている）か。

監査の深さの調整は設計AIが状況に応じて自律的に行ってよい（形式的な階層定義・発注者による事前レベル指定は設けない）。発注者側は、最終的な挙動確認（テストプレイ）を担う。監査結果を信じて先に進めるかどうかの意思決定は、発注者があらかじめ定めた基準（例：3観点とも合格なら進める、所定の停止条件に当たったときだけ発注者に判断を仰ぐ）に従って設計AIが行ってよい。基準の具体的な内容は運用ツール側のメモ・手順書に記す。

監査を通過した後、以下のテンプレートを用いて実装AIに1タスクずつ実行させる。いずれもチャット直接入力用であり、REQファイルは作成しない。
*   **通常時**: `TEMPLATE_REQ_TaskExecution_Lite.md`
*   **実行と同時に仕様を追加する場合**: `TEMPLATE_REQ_TaskExecution_Additional.md`
*   **未着手タスクの計画自体を修正する場合**: `TEMPLATE_REQ_TaskExecution_PlanningUpdate.md`（コード修正は行わない）

### 3-4. 【Step 3: 完了監査とクリーンアップ】

最終監査を行い、コミットとアーキテクチャ資料（`PROJECT_ARCHITECTURE.md`）の更新を行う。更新は「アーキテクチャに影響するサブフェイズの完了ごと」に差分追記する運用とし、全体の整形・清書はPhaseクローズ時にまとめて行ってよい。

サブフェイズ完了時は、DIRの「サブフェイズ一覧」の状態を「完了」に更新する。作業の結果、後続サブフェイズの分け方・実装要件を見直す必要が生じた場合も、この時点でDIRを書き換えて変更履歴に記録する（1-2節DIR参照）。

Phaseの最終タスクを除き、資料の更新は発注者側（人間＋設計AI）が行う。
実装AIは、資料に影響がある場合その旨を作業レポートに記述するのみであり、資料本体は書き換えない（2-0節参照）。

### 3-5. 【Phaseクローズ手順】

*   **引き金**: 発注者（人間）の主観判断のみ。設計AIは判定しない（1-1節参照：ゴール型は「使い物になった」、気分型は「妥協できる」と判断した時点）。
*   **手順**:
    1.  **棚卸し**: 該当Phaseの全RESに残る「懸念事項・要確認ポイント」を横断的に抽出する。あわせて、各RESの「開発資料の更新予定」と、Survey系RESの「開発資料との相違」節に「相違なし」以外が記載されているものを抽出する。
    2.  **仕分け**: 各項目を「次フェイズ／Interruptへ持ち越し」か「意図的に破棄」かに分類する。設計AIが仕分け案を出し、発注者が最終判断する。破棄する場合は理由を残す。
    3.  **記録**: Phaseごとの専用クローズレポートファイルは作らない（見返す際の手間が増えるため）。運用ツール側の進捗管理ファイル（例：`_doc/COWORK_STATUS.md`）に集約する。ただし「解決済み・決定済み」に仕分けた項目はそのファイルに残し続けず、要点と対応REQ/RESパスのみを退避用ファイル（例：`_doc/COWORK_STATUS_CLOSED.md`）へ追記し、進捗管理ファイル側からは削除する（コンテキスト肥大化・ハルシネーション誘発の防止）。進捗管理ファイルには「次フェイズ／Interruptへ持ち越す事項」「まだ判断が済んでいない懸念事項」のみを残す。
    4.  **アーキテクチャ資料の整合確認**: `PROJECT_ARCHITECTURE.md` の記載と実コードの乖離が疑われる場合は、調査REQ（パターンE／F）を発行し、実装AIに実コードの事実確認のみを行わせる（コード修正は絶対禁止）。

### 3-6. 【成果物の保管】

*   DIR保存場所: `_log/dir/`
*   REQ保存場所: `_log/req/`（チャット直接入力のREQは保存しない。1-3節参照）
*   RES保存場所: `_log/res/`
*   コミットメッセージは RESファイル名（拡張子抜き）で行う。タスクごとの随時保存は「ファイル名＋TASK1」などをコミットメッセージにする。
*   設計AIの知識ベース参照は、上記ファイル群を都度直接読み込むことで足りる（別途の登録作業は前提としない）。ただし、ファイルシステムへ直接アクセスできない運用ツールを用いる場合は、この限りではない（運用ツール側のメモを参照）。
