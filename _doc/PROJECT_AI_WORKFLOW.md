# OZFrameWorks AI駆動開発メソッド（発注者・設計AI専用マニュアル）

本ドキュメントは、人間（発注者）とリード設計AI／現場設計AIが、実装AIへ的確な作業指示（DIR/REQ）を出すための「発注ワークフロー」を定義したものである。

※ 実装AIのコンテキストノイズとなるため、**本ファイルは実装AIには参照させないこと**。実装AIが必要とする規範は、すべて各TEMPLATEファイル側に自己完結して記載する。
※ 本ドキュメントは特定のAI製品・ツール名を含まない、普遍的な運用ルールとして記述する。現時点でどのAI（ツール）が「リード設計AI」「現場設計AI」「実装AI」の各役を担っているかは、運用ツール側のメモ（例：`_doc/COWORK_HANDOFF.md`）を参照すること。

---

## 【登場人物（ロール）】

*   **発注者（頭脳）**: ユーザー（人間） ＋ 設計AI
    *   **リード設計AI**: フェイズ規模（アーキテクチャに影響する文脈を持つ）の開発に着手する際、大局的な指針書「DIR」を発行する。
    *   **現場設計AI**: リード設計AIが発行したDIR、または軽微な要件をもとに、実装AIへのREQ作成・RES監査（チェック0/1/2）を担当する。
*   **作業者（手足）**: 実装AI

※ 発注者側の「設計AI」は、上記の通りリード／現場の2役に分かれる。両者は必ずしも別セッション・別会話である必要はなく、同一AIが両役を兼ねてもよい（規模の小さい開発ではリード設計AIの工程＝DIR発行を省略し、現場設計AIがそのまま担当してよい）。

---

## 1. タスク規模の定義と用語

プロジェクトのタスクは、「文脈の連続性（タスク区分）」と「作業の複雑さ（アプローチ）」の2つの軸で柔軟に管理・運用される。

### 1-1. タスク区分（文脈の連続性）

*   **Phase（テーマ駆動型タスク）**
    *   **定義**: Phase全体で一つのテーマを持ち、アーキテクチャに影響を与えるような「連続した文脈」を必要とするタスク群（大規模リファクタリング、新機能群の追加、全体的なブラッシュアップなど）。
    *   **2つの型**:
        *   **ゴール型**: 達成目標を定めて開始するフェイズ（例：「キャンバスの拡縮・パン機能を入れる」）。実装を進める中でアイデアが膨らみ、細部フェイズが増えることもある。
        *   **気分型**: ゴールを定めずに開始するフェイズ（例：リファクタリング、UIブラッシュアップ）。
    *   **ステップ分割**: Phaseはさらにステップごとに分解し、`Phase XX-XX`（Phase番号-Step番号）といった表記で管理する。各ステップは「明確な単一機能の作業」に相当する。
    *   **終了条件**: Phaseの終了は常に「発注者（人間）の主観判断」による。ゴール型は「機能が使い物になった」と判断した時点、気分型は「現状で妥協できる」と判断した時点でクローズする。判定基準を事前に固定する必要はない（アジャイル的運用）。クローズ時の手順は3-5節を参照。

*   **Interrupt（単発・独立型タスク）**
    *   **定義**: 現在のPhaseのメインテーマとは直接関係しない、文脈の連続性を必要としない「単発で完結するタスク」の総称。
    *   不具合の修正（Bugfix）だけでなく、UIの微細な調整、既存機能の小拡張、パラメータのINI化などすべてを内包する。

### 1-2. DIR（設計指針書）/ REQ（作業指示）/ RES（作業レポート）

#### DIR（Directive）
* Phase（フェイズ規模・アーキテクチャに影響する文脈を持つ開発）に着手する際、リード設計AIが最初に発行する大局的な指針書。
* 「設計目的」「アーキテクチャ設計」「関連フォルダと物理ファイル構成」「実装AIを導くステップロードマップ」「懸念事項・後続への伏線」を含み、実装AI（および現場設計AIによるREQ/RES組み立て）が1歩も外れてはならない「北極星（制約事項）」として機能する。
* ファイル名: `YYYYMMDD_HHMM_DIR_(要件名).md`、保存先: `_log/dir/`。
* 規模の小さいPhaseや、Interrupt系のタスクではDIRを省略してよい（3-1節ケースA参照）。

すべての実装作業は「REQ → RES」の対で管理する。REQは「実装AIに対する正式な作業指示」、RESは「実装AIの作業結果を記録する正式な作業レポート」である。以後の修正・調査・リファクタリングは、このRESを起点として行う。

#### REQ（Request）
* 発注者が実装AIへ渡す作業指示書。作業目的、制約条件、対象ファイル、期待成果物を定義する。
* 実装AIはREQ以外の要求を推測せず、REQの範囲内でのみ作業を行う。

#### RES（Result Report）
* 実装AIが作業結果をまとめた作業レポート。実施内容、変更ファイル、作業方針、懸念事項、追加タスクなどを記録する。
* Phaseでは次工程の入力資料となる。

> 【運用上の注記】RESの完了報告（自己申告）は無条件には信用しない。実際の検証は、実装AIによる自己申告テキストではなく、**コミット前のGit diffレビュー**（REQで指定したファイル範囲と実差分の突合）と、**発注者自身によるテストプレイ**によって行う。この方針により、REQ/RESテンプレートに形式的な「受け入れ基準」「検証証跡」欄を必須項目として設けることはしない（トークンコストに見合わないため）。

### 1-3. ファイル名と相互リンク

*   **REQファイル名**: `YYYYMMDD_HHMM_(要件名).md`
    *   Phase作業中は `PhaseXX-XX_作業概要`
    *   Interruptは `Interrupt_作業概要`、ただし特定Phaseステップに対して明確な場合は `Interrupt_PhaseXX-XX_作業概要`
    *   調査指示は `Survey_調査内容`
*   **RESファイル名**: `YYYYMMDD_HHMM_(REQ要件名).md`
    *   ファイル名定義はREQ内に含める。基本的にはREQ要件名と同じとする。
*   **相互リンク**
    *   REQ → RES: REQ内に、出力すべきRESファイル名を明記する。
    *   RES → REQ: **RES冒頭に、参照元REQのファイル名を必ず記載させる。** タイムスタンプが異なるため、これがないと過去の追跡時に対応関係が壊れる（実際にREQファイルの上書き事故を検知する手がかりとなった実例あり）。

### 1-4. 作業規模とアプローチの選択（運用の柔軟性）

*   **大規模・複雑な作業（事前計画を伴うアプローチ）**: アーキテクチャの変更を伴う場合や、修正箇所が複数にまたがりハルシネーションのリスクがある場合は、必ず事前の計画立案を行わせ、タスクを分割してから順次実行させる。
*   **小規模・明確な作業（即時実行アプローチ）**: 修正箇所やロジックが明確であり、単一のタスクとして安全に完結できると判断した場合は、事前計画を立てず、単一の作業指示のみで即座に実行・解決させる。

## 2. 実装AIのスコープ規範

*   REQに明記されていないファイルは、閲覧はしてよいが**変更してはならない**。
*   「ついでの整形」「不要に見えるコードの削除」「命名の改善」は、明示指示がない限り禁止。
*   **実装AIとの対話は最小限にとどめる**（禁止ではない）。仕様のすり合わせ・設計の妥当性検証は、可能な限り発注者側（人間＋リード設計AI／現場設計AI）で事前に完了させ、実装AIには可能な限り精緻なDIR/REQを渡す。これはトークン従量課金コストの節約が目的であり、壁打ちそのものを一切禁じるものではない。
*   ただし、実装AIが作業中に真に判断できない曖昧点に遭遇した場合は、**推測で進めず**、作業を中断して疑問点を簡潔に1つ報告した上で発注者の回答を待ってよい。

## 3. 作業ワークフロー

### 3-1. 【Step 0: 企画検討と要求定義（発注者のみ）】

発注者間（人間＋リード設計AI／現場設計AI）でアーキテクチャを議論し、作業規模に応じて以下から最適なDIR/REQ/RESの組み合わせを選択する。

| ケース                                                               | 発注（DIR/REQ）                                                                  | 応答（RES）                                         |
| -------------------------------------------------------------------- | -------------------------------------------------------------------------------- | --------------------------------------------------- |
| A. Phase規模の本格的な実装（アーキテクチャに影響する文脈を持つ開発） | リード設計AIが`DIR`を発行 → 現場設計AIが`TEMPLATE_REQ_ImpretonPlanMake.md`を作成 | `TEMPLATE_RES_ImpretonPlan.md`                      |
| B. 軽微な新規作業（単一タスク規模）                                  | `TEMPLATE_REQ_Interrupt_Immediately.md`（計画なしで直接作業）                    | `TEMPLATE_RES_Interrupt.md`                         |
| C. 直前の作業のバグ修正                                              | `TEMPLATE_REQ_Interrupt_unImmediately.md`                                        | `TEMPLATE_RES_AddInterrupt.md`（直前RES末尾に追記） |
| D. 時系列が離れた過去のバグ修正                                      | `TEMPLATE_REQ_Interrupt_Immediately.md`                                          | `TEMPLATE_RES_Interrupt.md`（新規に単独レポート）   |
| E. 調査・コード監査（単一タスク規模）                                | `TEMPLATE_REQ_Interrupt_Immediately.md`（※コード修正の絶対禁止を厳命）           | `TEMPLATE_RES_Survey.md`                            |
| F. 調査・コード監査（複数タスク規模）                                | `TEMPLATE_REQ_ImpretonPlanMake.md`（※コード修正の絶対禁止を厳命）                | `TEMPLATE_RES_SurveyPlan.md`                        |
| G. 進行中計画の、未着手タスクへの軽微な要件追加                      | `TEMPLATE_REQ_TaskExecution_PlanningUpdate.md`                                   | 既存RESファイルを直接更新（別ファイルは作らない）   |

補足：
*   **A**: まずリード設計AIがPhase全体の大局的な指針として`DIR`を発行する（1-2節DIR定義参照）。現場設計AIはこのDIRを踏まえて`TEMPLATE_REQ_ImpretonPlanMake.md`を作成し、実装AIに詳細計画（RES）を立案させる。規模の小さいPhaseではDIR工程を省略し、現場設計AIが直接`TEMPLATE_REQ_ImpretonPlanMake.md`から開始してよい。計画立案後は、`TEMPLATE_REQ_TaskExecution_Lite.md` か `TEMPLATE_REQ_TaskExecution_Additional.md` を用いて、実装AIに「1タスク＝1チャット」で段階的にタスクを実行させ、タスクごとに作業レポートへ追記させる。
*   **D**: 過去の文脈を引きずらせないため、意図的に新規の単独レポートを立てさせる。
*   **E / F**: 目的は「実装AIの勝手な推測やコード改変を防ぎ、現在のコードの事実のみを抽出させる」こと。
*   **G**: 完了済みタスクの `[x]` ステータス・記述には一切触れず、未着手タスクの内容とアーキテクチャ設計のみを拡張する。前提が崩れるほどの大規模な計画破綻ではなく、あくまで軽微な要件追加を想定した経路。

### 3-2. 【Step 1: 計画立案（REQ → RES）】※計画立案を伴うREQのみ

発注者が実装AIへREQを投げ、実装AI自身に自分の理解度に基づいた細かなタスクリスト（RES）を構築させる。

### 3-3. 【Step 2: RES監査 → 作業実行（RES → Code）】

発注者（設計AI）は、上がってきた作業計画書（RES）に対し、必ず以下の**3つのチェックを1ステップずつ独立して**行う（視点のぼやけや見落としを防ぐため、まとめてチェックしない）。

1.  **チェック0（方向性・意図整合性）**: RESの作業内容が、そもそもREQ・発注者の意図の方向性と合っているか。
2.  **チェック1（ルール・責務違反／アーキテクチャ監査）**: Pull型監視の原則、Managerの巨大化、UIへの状態混入など、アーキテクチャの根幹を崩す設計になっていないか。
3.  **チェック2（スコープ・粒度）**: 変更単位が極力ファイル単位に分割され、実装AIがコンテキストを混同しない（安全なスコープに収まっている）か。

監査の深さの調整は設計AIが状況に応じて自律的に行ってよい（形式的な階層定義・発注者による事前レベル指定は設けない）。発注者側は、監査結果を信じて先に進めるかどうかの意思決定と、最終的な挙動確認（テストプレイ）を担う。

監査を通過した後、以下のテンプレートを用いて実装AIに1タスクずつ実行させる。
*   **通常時**: `TEMPLATE_REQ_TaskExecution_Lite.md`
*   **追加指示発生時**: `TEMPLATE_REQ_TaskExecution_Additional.md`

### 3-4. 【Step 3: 完了監査とクリーンアップ】

最終監査を行い、コミットとアーキテクチャ資料（`PROJECT_ARCHITECTURE.md`）の更新を行う。更新は「アーキテクチャに影響するステップの完了ごと」に差分追記する運用とし、全体の整形・清書はPhaseクローズ時にまとめて行ってよい。

### 3-5. 【Phaseクローズ手順】

*   **引き金**: 発注者（人間）の主観判断のみ。設計AIは判定しない（1-1節参照：ゴール型は「使い物になった」、気分型は「妥協できる」と判断した時点）。
*   **手順**:
    1.  **棚卸し**: 該当Phaseの全RESに残る「懸念事項・要確認ポイント」を横断的に抽出する。
    2.  **仕分け**: 各項目を「次フェイズ／Interruptへ持ち越し」か「意図的に破棄」かに分類する。設計AIが仕分け案を出し、発注者が最終判断する。破棄する場合は理由を残す。
    3.  **記録**: Phaseごとの専用クローズレポートファイルは作らない（見返す際の手間が増えるため）。運用ツール側の進捗管理ファイル（例：`_doc/COWORK_STATUS.md`）に集約する。ただし「解決済み・決定済み」に仕分けた項目はそのファイルに残し続けず、要点と対応REQ/RESパスのみを退避用ファイル（例：`_doc/COWORK_STATUS_CLOSED.md`）へ追記し、進捗管理ファイル側からは削除する（コンテキスト肥大化・ハルシネーション誘発の防止）。進捗管理ファイルには「次フェイズ／Interruptへ持ち越す事項」「まだ判断が済んでいない懸念事項」のみを残す。
    4.  **アーキテクチャ資料の整合確認**: `PROJECT_ARCHITECTURE.md` の記載と実コードの乖離が疑われる場合は、調査REQ（パターンE／F）を発行し、実装AIに実コードの事実確認のみを行わせる（コード修正は絶対禁止）。

### 3-6. 【成果物の保管】

*   DIR保存場所: `_log/dir/`
*   REQ保存場所: `_log/req/`
*   RES保存場所: `_log/res/`
*   コミットメッセージは RESファイル名（拡張子抜き）で行う。タスクごとの随時保存は「ファイル名＋TASK1」などをコミットメッセージにする。
*   設計AIの知識ベース参照は、上記ファイル群を都度直接読み込むことで足りる（別途の登録作業は前提としない）。
