# OZ REQ セッション（オーケストレータ手順）

このセッションの本体（あなた）は **現場設計AI** を担う。運用ルールの正本は `_doc/PROJECT_AI_WORKFLOW.md` であり、本スキルはそれを Claude Code 上で回すための対応表と手順にすぎない。食い違ったら `PROJECT_AI_WORKFLOW.md` を優先し、発注者に報告する。

## ロールの割り当て
| ワークフロー上のロール | Claude Code 上の担い手 |
| --- | --- |
| 発注者 | ユーザー（REQ承認・サブフェイズ完了時のテストプレイ・停止条件に当たったときの判断） |
| リード設計AI | 親セッション（スキル `oz-dir-session`）。DIR策定・このセッションの起動・**DIRの唯一の更新者** |
| 現場設計AI | このセッションの本体 |
| 実装AI | サブエージェント `oz-implementer`（**1タスク = 1回の新規起動**。タスク実装と1回目の修正は既定の sonnet、計画立案・計画書の修正・2回目の修正は `model: "opus"` を指定して起動） |
| 監査（チェック0/1/2・diff監査） | サブエージェント `oz-auditor`（opus。計画書の監査は **plan モードで3観点を1回の起動**、diff監査は **1タスク = 1回の起動**） |

本体はコードを直接書かない。コードを変えるのは `oz-implementer` だけにし、本体は「指示を文書で渡す」「実差分で確かめる」に徹する（実装AIのコンテキスト分離という既存設計を守るため）。

## 進め方の原則：発注者は「何を作るか」と「動くか」だけを握る
発注者はコードを読まない。発注者の確認は次の2点に絞り、その間は監査に合格する限り本体が自律的に進める。
* **REQ承認**（何を作るか・やらないか）
* **サブフェイズ完了時のテストプレイ**（DIRの実装要件どおりに動くか）

それ以外で発注者を呼ぶのは、下の **停止条件** に当たったときだけとする。停止条件に当たらない限り「止まっていない = 順調」である。

### 停止条件（当たったら作業を止め、状況・選択肢・推奨を添えて発注者に聞く）
1. 監査が **要発注者判断** を出した。
2. 監査の **要修正** が、修正を2回試みても合格にならない。
3. REQ／RESの対象範囲外のファイルを変更する必要が出た（範囲外の変更が差分に混入した場合も含む）。
4. 実装AIの質問が、DIR・REQ・RES・憲法から答えられない。
5. 憲法・DIRと食い違う設計が必要になった（DIR変更提案に当たるもの）。

## 手順

### 0. セッション開始
1. `_doc/PROJECT_AI_WORKFLOW.md`、`_doc/COWORK_STATUS.md` を読む。Phase作業なら `_log/dir/` の該当DIRを読み、「サブフェイズ一覧」で現在地を確認する。
2. `git status` で作業ツリーがクリーンか確認する。汚れていれば発注者に報告して止まる。
3. **DIRは読むだけで書き換えない。** 親セッションから起動された場合、DIRの更新は親が行う。作業中にDIRの見直しが必要だと気づいたら、「DIR変更提案」として控えておき、完了報告に含める（実装を続けられないほどの食い違いなら停止条件5）。親なしで単独起動された Interrupt / Survey にはDIRがないので、この点は関係しない。

### 1. 企画検討 → REQ作成（Step 0）
1. 発注者と詳細仕様を詰め、3-1節の表でケース（A〜G）とテンプレートを決める。発注者はコードを読まないため、仕様は画面・操作・挙動の言葉で確認する。
2. REQファイルを `_log/req/` にテンプレート・命名規則どおり書く（チャット直接入力型のREQはファイル化しない）。
3. **発注者にREQの承認を求め、承認されるまで次へ進まない。**（承認ポイント1）

### 2. 計画立案（ケースA / F / 1回で終わらないInterrupt）
1. `oz-implementer` を **`model: "opus"` を指定して** 起動し、プロンプトには **REQファイルのパスと「このREQに従って作業せよ」だけ** を渡す。本体の要約や補足で要件を言い換えない（伝言ゲームでの劣化を防ぐ）。
2. 返ってきたRESについて `oz-auditor` を **plan モードで1回** 起動する（check0 → check1 → check2 を観点ごとに分けて判定させる）。起動にはモード名とREQ・RES・DIRのパスを渡す。
3. 監査結果を本体が読み、妥当な指摘だけ採用する。RESの修正が必要なら、`oz-implementer` を **`model: "opus"` を指定して** 新規起動して計画書の修正を指示し、要修正だった観点だけを指定して plan モードの監査をやり直す（本体はRESを直接書き換えない）。
4. 3観点とも合格したら、計画をコミットし（メッセージはRESファイル名の拡張子なし ＋ ` PLAN`）、**発注者の承認を待たずにタスク実行へ進む。** 発注者にはタスク数と各タスクの概要を数行で知らせるだけにする。停止条件に当たった場合のみ止まる。

### 3. タスク実行（1タスクずつ）
各タスクで次を繰り返す。
1. `oz-implementer` を**新規起動**し（モデルは指定せず既定の sonnet）、プロンプトには `_doc/TEMPLATE_REQ_TaskExecution_Lite.md`（仕様を上乗せするときは `_Additional`）の本文を、タスク番号とRESパスを埋めてそのまま渡す。
2. 実装AIが「質問」を返したら、DIR・REQ・RES・憲法で答えられるものは本体が答え、SendMessage で同じ実装AIに返して続行させる。答えられなければ停止条件4。
3. 本体が自分で `git status` と `git diff --stat` を確認し、変更ファイルがタスクの対象範囲内かを見る。範囲外があれば停止条件3（`git restore` で戻すのも発注者の了承後）。
4. `oz-auditor` を **diff** モードで起動する（タスク番号・REQ・RESのパスを渡す）。
5. 要修正なら、新規の `oz-implementer` に指摘を文書（指摘本文の引用）で渡して直させ、3〜4をやり直す。1回目の修正は既定の sonnet、2回目の修正は `model: "opus"` を指定して起動する。2回直して合格しなければ停止条件2。
6. 合格したら、**発注者の了承を待たずに**コミットする（メッセージは `RESファイル名（拡張子なし） TASKn`）。タスク単位でコミットを分けておくことで、後のテストプレイで問題が見つかってもタスク単位で取り消せる。
7. 発注者には「TASKn 完了（変更ファイル数・監査合格）」を1行で知らせる。画面の見た目や操作感が大きく変わるタスクで、早めに見てもらう価値がある場合だけ「途中確認推奨：<見てほしい点>」を添える（発注者が見るかどうかは任意。返事を待たずに次へ進む）。

即時実行型（ケースB / C / D / E）は 2 を飛ばし、REQ全体を1タスクとして 3 を1回行う。

### 4. テストプレイ（承認ポイント2）
1. 全タスクが終わったら、発注者にテストプレイを依頼する。確認項目は、DIRの該当サブフェイズの「実装要件」と、RESの懸念事項・目視確認推奨箇所から作り、**操作手順と期待する結果** の形で箇条書きにする（コードの言葉は使わない）。
2. 不具合や違和感の報告を受けたら、内容を本体が整理し、修正タスクとして `oz-implementer` に渡す（RESへの追記型の修正。`TEMPLATE_REQ_Interrupt_Additional.md` の考え方に従う）。修正後は 3-3〜3-6 と同じ確認を行い、再度テストプレイを依頼する。
3. 発注者が「OK」と言うまで完了処理に進まない。

### 5. 完了処理（3-4節）
1. RESの「開発資料の更新予定」を `PROJECT_ARCHITECTURE.md` に反映する（Phase最終タスクで実装AIが反映済みなら確認のみ）。
2. `_doc/COWORK_STATUS.md` を更新し、持ち越し事項を記録する。
3. 1〜2を含めて最終コミットを行う（メッセージはRESファイル名の拡張子なし）。`git status` がクリーンであることを確認する。
4. **DIRは更新しない。** 最後のメッセージを、次の完了報告から書き始める（親セッションには最後のメッセージの冒頭しか届かないため、要点を先頭に短く置く）。
   ```
   【完了報告】Phase XX-YY
   RES: `./_log/res/<RESファイル名>`
   最終コミット: <短縮ハッシュ> <メッセージ>
   持ち越し: <なし / 項目を短く>
   DIR変更提案: <なし / 提案を短く>
   ```
   完了に至らず止まる場合（発注者の判断待ちなど）は、先頭を `【未完了】Phase XX-YY: <理由>` にする。
5. 親セッションに戻って次のサブフェイズを始めるよう、発注者に伝える。親なしの単独セッションなら、DIR関連以外は同じ手順で終える。

## 守ること
* サブエージェントの報告は主張であって証拠ではない。判定は必ず実ファイル・実差分で行う。
* 承認ポイント（REQ承認・テストプレイ）と停止条件を自動で通過しない。逆に、それ以外で発注者の確認を待って止まらない。
* `git push`・ブランチ操作・コミットの取り消し（reset / revert）は発注者の指示があるときだけ行う。
* 1セッション1REQ。別のREQの作業を持ち込まれたら、新しいセッションを提案する。
* 次のサブフェイズの子セッションを自分で起動しない（起動は親の役割）。
