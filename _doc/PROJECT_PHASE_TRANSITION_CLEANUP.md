# PROJECT_PHASE_TRANSITION_CLEANUP.md
## フェイズ大番号移行時における「ドキュメント・実行ログ棚卸し」定型プロセス

---

### このファイルについて
* **実行者**：Phase親セッション（リード設計AI、スキル `oz-dir-session`）。新しいPhaseのDIR策定前に行う。
* **目的**：プロジェクトのフェイズ大番号が移行する際（例：Phase 1 → Phase 2）、それまでの開発で肥大化したドキュメント群・実行ログを棚卸し・スリムアップ（デフラグ）する。開発の中盤から後半にかけてAIのワーキングメモリが不要な過去データで汚染され、ハルシネーションや先祖返り（不整合な提案）を起こす不具合を、構造的・恒久的に防止することが狙い。
* **実行タイミング**：フェイズ大番号の完了RESコミット直後、次のフェイズ大番号のDIR策定前。
* **やらないこと（Non-goals）**：実コード（`.js`等）の変更・機能追加は一切行わない。`PROJECT_CONSTITUTION.md`（憲法）の簡略化も対象外。

### 2. `PROJECT_ARCHITECTURE.md`の監査基準
記述をノイズのないドライな状態に保つため、以下3点で推敲・削除する。

1. **コード追従の徹底排除**：「コードを直接読めばわかる詳細」（ローカル変数名、詳細なループ処理、個別プロパティの代入、一時変数のバッファリング等）を削り、不変の「インターフェース契約（メソッド名・引数の型と意味・戻り値の型と意味）」と「クラス間の依存・呼び出し関係」のみに絞る。
2. **無駄な比喩・冗長表現の排除**：「司令塔のように振る舞い、命令をシャワーのように注ぎ込む」のような文学的な誇張表現・比喩を排し、事実・幾何数式・構造的依存関係のみを正確かつ冷徹なエンジニアリング表現で記述する。これらの修飾はAIが仕様を誤解・歪曲する原因になる。
3. **多重表記・重複情報の排除**：`PROJECT_CONSTITUTION.md`等の他SSOT（単一の真実）資料と同内容の重複記述（フォルダ構造、REQ/RESルール、絶対禁止事項など）を発見した場合、該当セクションごと削除し、参照リンク（例：「憲法第x章を参照」）のみにする。

---

### 3. `COWORK_STATUS.md`のスリムアップ基準
過去のバグ修正や中間状態の不整合な経緯にAIが引っ張られて「先祖返りバグ」を起こすのを防ぐため、ワーキングメモリを物理的に制限する。

1. **要約の凝縮**：完了したPhase全体の詳細タスクチェックリストや作業プロセス記述はすべて削除し、1〜3行程度の「設計上の到達点・確定仕様」（例：「P1-7で円・弧がEllipse.jsに一元化されて本実装接続された」）のみに要約して履歴セクションへ結合する。
2. **詳細情報の物理退避**：完了した個別タスク、解決済みの詳細な懸念事項、テストプレイ時の不具合ログ等は、すべて本ファイルから物理的にカットし、`COWORK_STATUS_CLOSED.md`の末尾へ移設する。本ファイルには「現在進行中の作業」「未解決の懸念事項（バックログ）」のみを残す。
3. **ハルシネーション防御**：`COWORK_STATUS_CLOSED.md`は通常セッションで読み込まない。過去のデバッグ経緯を確認したいときのみ、明示的に参照する。

---

### 4. 実行ログ（`_log/req/`・`_log/res/`・`_log/dir/`）のアーカイブ基準
フェイズが進むごとに際限なく増え続ける生ログを、大番号移行のタイミングでまとめて退避する。

1. **移動対象**：移行元フェイズ大番号（例：Phase 1）に属するREQ・RES・DIRファイルを全件対象とする。一部だけを残す選別は行わない。
2. **移動方法**：`git mv`で対応する`closed/`サブフォルダへ、Git履歴を保ったまま物理移動する。
3. **移動後の参照更新はしない（意図・根拠）**：`COWORK_STATUS_CLOSED.md`やRESファイル冒頭の「参照元REQ」「参照元DIR」逆リンク等、既存ドキュメント内に記載済みの移動前パス（例：`_log/res/260808_1835_...`）は遡って更新しない。過去ログを実際に辿る際は、記載されたファイル名でリポジトリ内をgrepし、`closed/`配下から探す。この判断が安全に成立する根拠は以下の3点：
    *   **前提1章の「全件移動」がペアの整合性を担保する**：REQ・RES・DIRを選別せず全件同時に`closed/`へ移すため、あるファイルが`closed/`にあれば、それが参照する側・される側のファイルも必ず同じ`closed/`側にある（移動ミスがない限り）。一部だけ残す運用に変えた場合はこの前提が崩れるため、絶対に選別移動をしないこと。
    *   **ズレ方が完全に決定論的**：stale化したパスは常に「`_log/req/`→`_log/req/closed/`」のように`closed/`を1階層挟むだけの同一パターンでしか壊れない。ファイル名部分は不変なので、grep一発で確実に見つかる。必要になれば全文置換で一括修復することも可能（現状はその必要がないため未実施）。
    *   **closed後にREQ↔RES↔DIRを同時参照する必要性が低い**：REQ/RESの突き合わせ監査（チェック0/1/2）はPhaseが進行中・未クローズの段階で完了しており、クローズ後の参照は大半RESの内容だけで事足りる。REQやDIRの原文まで遡る必要が生じるのは稀なケースであり、そのたびにgrepする程度のコストは許容範囲。
    *   **残留リスク**：現状これらのパスをプログラム的にパースする自動化は存在しないため実害はない。将来、req/res履歴を機械的に集計・リンク解決するツールを作る局面が来た場合は、この「更新しない」方針自体を再検討すること。
4. **`_log/dir/`の可視性（絶対厳守）**：`_log/dir/`（`closed/`含む）は意図的に`PROJECT_ARCHITECTURE.md`のフォルダ構造に記載しない。DIRは実装AIに直接読ませない設計（DIR→REQへの変換時に内容を意図的に変えるため）であり、実装AIが参照する`PROJECT_ARCHITECTURE.md`にパスを載せるとこの隔離が破られる。所在は`_doc/PROJECT_README.md`・`PROJECT_AI_WORKFLOW.md`側の記載のみで完結させる。本作業のたびに、誤って`PROJECT_ARCHITECTURE.md`へ`_log/dir/`を追記しないこと。

---

### 5. 実行手順
1. 移行元フェイズ大番号に属するREQ・RES・DIRファイルを洗い出し、`git mv`で各`closed/`サブフォルダへ移動する（4章の基準に従う）。
2. `PROJECT_ARCHITECTURE.md`を2章の基準で監査・スリムアップする。削除内容が仕様の実質的な変更に見える箇所は、確定前に発注者へ差分を提示して確認を取る。
3. `COWORK_STATUS.md`を3章の基準でスリムアップし、詳細を`COWORK_STATUS_CLOSED.md`へ退避する。
4. 変更ファイルをコミットする（コミットメッセージ例：`docs: phase cleanup and status defragmentation`）。**GitHubへのpushは発注者（人間）が行う。**
