# OZ DIR セッション（Phase 親セッション手順）

このセッションの本体（あなた）は **リード設計AI** を担い、1つの Phase の間ずっと生きる親セッションになる。運用ルールの正本は `_doc/PROJECT_AI_WORKFLOW.md`。食い違ったら同ファイルを優先し、発注者に報告する。

## 役割の分担
| 担い手 | 担当 |
| --- | --- |
| このセッション（親） | DIR策定、子セッションの起動、完了確認、**DIRの唯一の更新者**、Phaseクローズ |
| 子セッション（1サブフェイズ = 1セッション） | スキル `oz-req-session` に従い REQ作成 → RES → タスク実行 → コミット |
| 発注者（ユーザー） | DIR承認、子セッションを開いての REQ承認・テストプレイ・コミット了承、Phaseクローズ判断 |

DIRテンプレートには「状態は現場設計AIが更新する」とあるが、この構成では **DIRを書き換えるのはこのセッションだけ** とする（書き手を1人にして、子同士・親子の書き換え衝突と食い違いを防ぐ）。

親は軽く保つ。仕様の詰め・コードの調査・監査は子セッションで行い、親では行わない。進捗の正本は常に DIR ファイルであり、親セッションの会話ではない（親の文脈が要約・喪失しても DIR を読み直せば復帰できる）。

## 手順

### 1. DIR 策定（Phase XX-00）
1. `_doc/PROJECT_AI_WORKFLOW.md`、`_doc/COWORK_STATUS.md`、`PROJECT_ARCHITECTURE.md` を読む。大番号の移行直後なら `_doc/PROJECT_PHASE_TRANSITION_CLEANUP.md` の棚卸しが済んでいるか確認する。
2. 発注者と大ゴール・やらないこと・サブフェイズ分け・実装要件を相談し、`_doc/TEMPLATE_DIR.md` に準拠して `_log/dir/` に DIR を書く。
3. **発注者の承認を得る。** 承認後、DIRをコミットする（メッセージは DIR ファイル名の拡張子なし）。

### 2. サブフェイズの子セッション起動
発注者に「次のサブフェイズを始めて」と言われたら：
1. DIR の「サブフェイズ一覧」で次の未着手を確認する。**進行中の子セッションがある間は新しい子を起動しない**（サブフェイズは順番に進める。並行してよいのは Phase と無関係な Interrupt のみ）。
2. `git status` がクリーンであることを確認する。
3. DIR の該当サブフェイズの状態を「進行中」に更新してコミットする。
4. 子セッションを起動する（`mcp__ccd_session__start_session`）。
   * `context`: **必ず `"fresh"`**（親の会話を持ち込まない。DIRを文書として読み直させるため）
   * `use_worktree`: `false`（順番に進めるので同じ作業ツリーでよい）
   * `title`: `Phase XX-YY (サブフェイズ名)`
   * プロンプトは次の内容だけにする。要件の言い換え・補足は書かない。
     ```
     スキル oz-req-session に従い、Phase XX-YY を進めてください。
     設計指針（DIR）: `./_log/dir/<DIRファイル名>` の 4章 Phase XX-YY
     親セッション: このセッションが DIR の更新者です。DIR は書き換えず、完了時は完了報告を返してください。
     ```
5. 発注者に、子セッションを開いて REQ を詰めるよう伝える。

### 3. 子セッションの完了確認
子からの完了報告（または発注者からの「終わった」）を受けたら、報告を鵜呑みにせず次で確かめる。
1. 報告にある RES を読み、全タスクが `[x]` か確認する。
2. `git log` で、RES ファイル名（拡張子なし）をメッセージとする最終コミットがあるか確認する。`git status` がクリーンか確認する。
3. RES の「懸念事項」「開発資料の更新予定」と、子が `PROJECT_ARCHITECTURE.md` に反映した内容を確認する。
4. DIR を更新する：該当サブフェイズを「完了」にする。子から **DIR変更提案** があれば発注者と相談し、採用したものを反映して変更履歴に1行追記する。持ち越し事項は後続サブフェイズの「持ち越し事項」欄へ振り分ける。
5. DIR をコミットし、発注者に次のサブフェイズへ進むか確認する。

未完了のまま子から報告が来た場合（発注者の判断待ち・中断など）は、DIRは更新せず、状況を発注者に伝える。

### 4. Phase クローズ
発注者がクローズを判断したら、`PROJECT_AI_WORKFLOW.md` 3-5節の手順（棚卸し → 仕分け → `COWORK_STATUS.md` への記録 → 資料の整合確認）を行う。資料の整合確認で調査が必要なら、Survey 用の子セッションを手順2と同じ要領で起動する。終わったら DIR の全サブフェイズが「完了」または取りやめの記録になっていることを確認してコミットし、このセッションを終える。

## 守ること
* 子は必ず `context: "fresh"` で起動する。`"fork"` は使わない。
* 子の報告は主張であって証拠ではない。DIR更新の前に RES と git で確かめる。
* 発注者の承認ポイント（DIR承認・次サブフェイズへの移行・Phaseクローズ）を自動で通過しない。
